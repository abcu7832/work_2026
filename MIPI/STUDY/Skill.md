## 1. rtl-area-power-optimization

**목적**: RTL 수준에서 면적 감소 및 불필요한 스위칭 감소.

**핵심 규칙**:
- 합성 계층/리소스 리포트를 활용해 실제 핫스팟 찾기
- 임팩트가 큰 구조부터 줄이기 (Boolean 정리보다 우선)
- 버퍼·FIFO·슬롯·페이로드 폭·채널 수 등 적정 크기 유지
- 대형 레지스터 배열 대신 메모리 구현 고려
- 동시에 수행되지 않는 연산은 리소스 공유(time-multiplex) 고려
- 필요 없는 리셋 최소화 (datapath가 사용 전 overwrite 보장 시)
- 의미 있는 enable로 불필요한 레지스터 전이 줄이기

**최적화 순서**:
1. 지배적 RTL 리소스 식별
2. 메모리/버퍼 depth·width·포트 수 감소
3. 중복 고비용 리소스 제거/공유
4. 불필요한 레지스터/리셋 제거
5. 중복 조합 로직 감소
6. 불필요한 스위칭 감소
7. 재합성 후 재평가

## 2. rtl-bandwidth-performance

**목적**: RTL 데이터 이동·버퍼링·트랜잭션 형태·사이클 동작 평가로 DDR 트래픽 감소 및 처리량 확보.

**핵심 규칙**:
- 외부 메모리 트래픽을 아키텍처 비용으로 취급
- 불필요한 중간 DDR write/read 왕복 최소화
- 가능하면 `read once → 내부 처리 → write once` 패턴 사용
- 라인/블록/타일 데이터를 내부 버퍼에서 재사용
- burst-friendly 트랜잭션 유지
- 주소 생성 패턴으로 인한 불필요한 트랜잭션 단편화 방지
- FIFO/큐로 생산자-소비자 속도 불일치 및 메모리 레이턴시 흡수
- 처리량(throughput)과 레이턴시(latency)를 분리해서 추적

**DDR 상세 데이터 없을 때 최소 워크플로우**:
1. 외부 read/write 카운트
2. 중간 데이터(쓰고 다시 읽는 것) 식별
3. 온칩에 머물 수 있는 재사용 데이터 식별
4. 단위 작업당 사이클 측정/추정
5. 스톨/백프레셔 위치 파악
6. FIFO/큐 경계 점검
7. 노미널 vs 워스트케이스 모드 비교

## 3. rtl-hardware-design

**목적**: 합성 가능한 RTL 설계·리뷰·리팩토링·설명. Pong P. Chu의 *RTL Hardware Design Using VHDL* 방법론 기반.

> 기본적으로 Verilog/SystemVerilog 예시 사용. VHDL은 명시 요청 시만.

**핵심 설계 규칙 (20가지)**:
1. HDL 작성 전 하드웨어(레지스터·FU·MUX·라우팅) 먼저 생각
2. 합성에 알고리즘 수정 기대 금지 — 아키텍처는 설계자 책임
3. HDL 구조체를 하드웨어로 해석 (연산자 → FU, 조건 → 라우팅)
4. 필요 없는 기능 명세 금지 (불필요한 하드웨어/제약 발생)
5. 리소스 공유 시 MUX·라우팅·타이밍 오버헤드 포함해 평가
6. 공통 연산은 공유 데이터패스로 구현
7. 감소·선택·시프터·산술 등은 위상(cascade/tree/prefix 등) 명시적 결정
8. 파라미터화는 아키텍처 수준에서 — 스케일 시 구조 유지
9. 일반 순차 동작은 동기(synchronous) 방식 선호
10. 클록을 일반 RTL 신호로 조작 금지
11. 저장소와 조합 next-value 로직 분리
12. FSMD에서 데이터패스와 제어패스 구분
13. 레지스터 전송은 클록 엣지에서 업데이트 (delayed-store 의미론)
14. 알고리즘을 하드웨어에 맞게 재공식화 후 번역
15. 데이터 의존성과 병렬 가능성 분석
16. 스케줄링·바인딩을 명시적 설계 결정으로
17. 파이프라인 레지스터는 타이밍 기준으로 배치 (기능 경계 아님)
18. 라이프타임 비겹치는 중간값 레지스터 공유
19. 계층 구조는 복잡성 관리·재사용·합성 제어에 활용
20. 특수 하드웨어·CDC 경계는 명시적으로 격리

**CDC 규칙**:
- 단일 비동기 신호는 한 곳에서만 동기화 후 팬아웃
- 관련 멀티비트 신호는 독립 동기화 금지
- 소스 레지스터된 신호를 동기화기 입력에 선호

## 4. rtl-ip-development-methodology

**목적**: ASIC RTL/알고리즘 IP 개발 전 단계 (Feasibility → Spec → Ref SW → RTL → SIM → 검증 → Integration → FPGA → Synthesis) 계획·리뷰·실행.

**개발 단계**:

| Phase | 이름 | 목표 | Quality Gate |
|---|---|---|---|
| 0 | Explore & Feasibility | 구현 대안 열거, 실현가능성 검토 | 팀 구현 방향 합의 |
| 1 | Spec Freeze | 기능·인터페이스·레지스터맵·포맷·성능 동결 | 크로스 리뷰 완료, 스펙 동결 |
| 2 | Ref SW | 알고리즘 SW 레퍼런스 모델 개발 및 검증 | 회귀 통과, 알고리즘 크로스 리뷰 |
| 3 | RTL | 동결된 스펙에 따른 합성 가능한 RTL 구현 | 합성 가능, lint 클린, AI 리뷰, 크로스 리뷰 |
| 4 | SIM Environment | TB 및 외부 모델 환경 구축 | 스모크 케이스 통과 (compile→run→check) |
| 5 | Unit Verification | RTL SIM 출력 vs SW HW 모델 비교 | 출력이 명시된 허용 오차 내 일치 |
| 6 | Coverage & Case Generation | 지시적·랜덤 케이스 + 커버리지 | 기능 커버리지 목표 달성, 미해결 실패 = 0 |
| 7 | System/Top Integration | 인터페이스·핸드셰이크·성능·CDC 검증 | E2E 골든 매치, 성능 목표, CDC 클린 |
| 8 | FPGA | 실 센서 타이밍, 실시간 처리량, 장시간 안정성 | 온타깃 골든 매치, 장시간 안정 동작 |
| 9 | Synthesis | PPA 및 RTL/넷리스트 동등성 확인 | 타이밍 클로저, 면적 목표, LEC 통과 |

**설계 품질 속성**:
- 성능/주파수 (타이밍 마진 포함)
- 면적, 저전력
- 유연성/확장성, 재사용성
- 유지보수성, SW 친화성 (HW/SW 공동 설계)
- 신뢰성/견고성, 테스트 용이성

## 5. rtl-maintenance

**목적**: 기존 Verilog/SystemVerilog RTL의 안전한 분석·디버깅·수정·리뷰. 최소한의 변경으로 동작 보존.

**운영 원칙**:
- 변경 전 이해 먼저
- 요청 사항이 명시적으로 요구하지 않으면 기존 동작 보존
- 근본 원인에 직접 대응하는 가장 작은 변경 선호
- 기존 프로젝트 구조·네이밍·코딩 스타일 보존
- 기능 수정에 무관한 cleanup/리팩토링 혼합 금지

**핵심 유지보수 규칙 (12가지)**:
1. 수정 전 현재 동작 재구성 (신호 생산→레지스터→소비 경로 추적)
2. 증상이 아닌 근본 원인 수정
3. 변경 범위 최소화 (무관한 rename/refactor/reformat 금지)
4. 타이밍·프로토콜·동작 계약 보존 (레이턴시·펄스폭·핸드셰이크 등)
5. 신호를 이름이 아닌 의미론(level/pulse, 동기/조합 등)으로 처리
6. 제어 로직 변경 시 조합 의존성(피드백 루프) 확인
7. 기본적으로 기존 인터페이스 보존
8. 설명 안 된 레거시 로직을 가볍게 삭제 금지
9. 프로젝트 코딩 스타일 및 코드 밀도 보존
10. 필수 수정 vs 선택적 개선 분리
11. 변경된 로직으로부터 회귀 범위 정의
12. 문제·원인·수정·리스크를 각각 구분해서 설명

**응답 형식** (비자명 버그/리뷰 시):
- **문제** / **원인** / **수정** / **영향 가능성·회귀 확인**

## 6. rtl-project-design-guidelines

**목적**: 팀 공통 RTL IP 설계 규칙 적용 (품질 속성·타이밍 경계·코딩 스타일·명명·클록/리셋·APB/AXI 인터페이스·래퍼·인프라·고정소수점 표기법).

**IP 설계 품질 속성**:
- 성능/주파수 (타이밍 클로저 마진 포함)
- 면적 최소화, 저전력 (클록 게이팅, 불필요한 전이 최소화)
- 유연성/확장성 (파라미터화), 재사용성, 유지보수성
- OS/SW 친화성, 신뢰성/견고성, 테스트 용이성

**타이밍 지향 프로젝트 규칙**:
- 프로세스 메모리 입출력 주변에 레지스터 슬라이스
- 멀티플라이어 앞뒤에 레지스터 슬라이스 (타이밍 요구 시)
- IP 출력 레지스터 슬라이스
- IP 입력 레지스터 슬라이스 (타이밍·피드백 의존성 요구 시만)

**코딩 규칙**:
- ANSI 스타일 인라인 포트 선언 사용
- 탭/스페이스 혼합 금지
- 유용한 정보 추가 시에만 주석 작성

**명명 규칙**:

| 항목 | 규칙 |
|---|---|
| 포트 | 대문자 |
| 클록 | `IP_GROUP_CLK`, `IP_GROUP_CE` 패턴 |
| 리셋 | `IP_GROUP_(S)RST(N\|n)` 패턴 (동기 리셋 시 S 포함, 극성 명시) |
| define/parameter/localparam | 대문자 |
| module | 소문자 |
| instance | 대문자 |

**인터페이스 포트 순서**:
- APB: `PCLK, PRESETn, PADDR, PSEL, PENABLE, PWRITE, P(W)STRB, PREADY, PRDATA, PSLVERR`
- AXI: 관련 AXI 스펙 순서 따름

**고정소수점 표기**:
- `unsigned Qm.n` / `signed Qm.n` (signed의 m은 부호 비트 포함)
- 예: `unsigned Q2.10`, `signed Q3.8`

## 7. rtl-reset-gating-dft

**목적**: RTL에서 안전한 비동기 리셋 사용 강제. 기능 신호의 비동기 리셋 경로 혼합 방지.

**핵심 규칙**:
> 플립플롭의 비동기 리셋 핀은 오직 리셋 트리 신호로만 구동되어야 한다.

**금지 패턴**:
```verilog
wire local_rstn = RSTN && !CLEAR_REQ;  // 기능 신호와 리셋 AND
always @(posedge CLK or negedge local_rstn) begin
    if (!local_rstn) ...
end
```

**권장 패턴**:
```verilog
always @(posedge CLK or negedge RSTN) begin
    if (!RSTN)          ...  // 비동기 리셋
    else if (CLEAR_REQ) ...  // 동기 클리어
    else                ...
end
```

**이 규칙이 존재하는 이유**:
- **DFT/Scan**: ATPG는 비동기 reset/set이 shift/capture 동안 비활성화 필요. 기능 로직이 혼합되면 DRC 위반, ATPG 제약, test-point 삽입 발생
- **리셋 아키텍처**: 게이팅된 리셋은 추가 리셋 도메인으로 취급되어 IP 재사용성 저하
- **글리치 위험**: 조합 로직 글리치가 클록 정지 중에도 비동기 리셋 직접 트리거 가능
- **STA**: 기능 로직이 리셋 해제 경로에 있으면 recovery/removal 타이밍 경로 생성

**체크리스트**:
- [ ] 비동기 리셋 소스가 리셋 트리만인가
- [ ] 기능 신호가 리셋을 게이팅/생성하지 않는가
- [ ] 게이팅된 리셋이 새로 자식 모듈로 전파되지 않는가
- [ ] 기능 클리어는 가능하면 동기 방식인가
- [ ] 리셋값과 우선순위가 보존되는가
- [ ] Scan/DFT 동작이 기능 상태에 의존하지 않는가
- [ ] 클록 정지 동작이 고려되었는가

## 8. rtl-structural-safety

**목적**: 합성 가능한 RTL 변경 시 구조적 위험(조합 피드백 루프·핸드셰이크 의존성 루프·의도치 않은 래치·생성된 클록·안전하지 않은 비동기 제어·누락된 레지스터 경계) 검토.

> 기능 시뮬레이션 통과만으로는 충분하지 않음.

**핵심 원칙**: 지역적으로 합리적인 조합 표현식도 전역 구조적 위험을 만들 수 있음. 모듈 경계는 조합 경로를 끊지 않음.

**주요 검토 항목 (14가지)**:
1. **조합 피드백 루프**: 레지스터 없이 자기 자신으로 귀환하는 경로 금지
2. **고위험 핸드셰이크 패턴**: VALID↔READY, REQ↔ACK, PUSH↔FULL 등 양방향 추적
3. **READY/VALID 규칙**: 닫힌 의존 루프(`upstream VALID → downstream READY → upstream VALID`) 금지
4. **순차 경계 확인**: 어느 레지스터가 어느 사이클에 이벤트 관찰/응답 생성하는지 명시
5. **비동기 제어 안전**: discard/clear/flush 등 기능 신호로 비동기 리셋/셋/클록 생성 금지
6. **생성/게이팅 클록 규칙**: 일반 조합 RTL로 클록 생성/게이팅 금지 (`wire local_clk = CLK & enable`)
7. **래치 추론**: `always @*`에서 모든 경로에 출력 할당 확인, 디폴트 누락 주의
8. **글리치 → 민감 제어**: 비동기/엣지 센서 목적지 구동 전 멀티텀 조합 로직 검토
9. **CDC 인식**: 클록 도메인 교차 신호 수정 시 동기화 방법 확인
10. **제어 펄스 의미론**: 루프 해소용 레지스터 삽입 시 펄스 손실/연장/병합 여부 확인
11. **최소 수정 원칙**: 정확한 의존 사이클 식별 후 가장 작은 경계만 삽입
12. **필수 구조 검토 체크리스트**: 패치 전 모든 피드백 경로 확인
13. **리뷰 출력 형식**: 수정 신호→의존 경로→루프 닫힘 위치→시뮬레이션이 정상으로 보이는 이유→리스크→최소 수정→사이클 변화→회귀 케이스 순으로 설명
14. **회귀 우선순위**: 동일 사이클 핸드셰이크·백프레셔·FIFO 경계·단일 사이클 펄스·discard/flush 중 트래픽 등

## 9. rtl-timing-optimization

**목적**: 크리티컬 패스 단축, 파이프라인/레지스터 슬라이스 계획, 타이밍 지향 RTL 리뷰, 타이밍 QoR 개선.

> 가용 시 합성/STA 결과를 진실의 원천으로 사용.

**핵심 규칙**:
- 측정된 크리티컬 패스 최적화 (복잡해 보이는 코드 기준 아님)
- 긴 조합 체인을 의도적으로 끊기
- 타이밍 민감 IP/데이터패스는 출력 레지스터 슬라이스 선호 (레이턴시 허용 시)
- 멀티플라이어 전후에 레지스터 슬라이스 고려
- 모듈/기능 경계가 아닌 딜레이 기준으로 파이프라인 스테이지 균형 조정
- valid/enable/last/메타데이터/주소/태그를 파이프라인 데이터와 함께 지연
- ready/valid, req/ack, done, 백프레셔 의미론 보존
- 의미 있는 구조 변경마다 합성/STA 재실행

**실용 패턴 (프로젝트 작업 기반)**:
- 메모리/FIFO 출력 레지스터 슬라이스
- 멀티플라이어 피연산자/결과 파이프라인
- 파이프라인 평균 계산 데이터패스
- 다운스트림 ready 피드백 해소용 입력 큐
- 객체/프레임/APB 설정 스냅샷
- SEQ/META 스타일 등록 출력
- 샘플 카운트 파이프라인
- 패킷 사전 패킹 레지스터
- 커맨드 큐/이슈 레지스터

**워크플로우**:
1. 타이밍 리포트 확보
2. 시작점·끝점·지배 로직 식별
3. 경로를 RTL에 매핑
4. 딜레이 분류 (산술/MUX 우선순위/제어/팬아웃·라우팅/모듈 간 교차/혼합)
5. 가장 작은 유용한 레지스터 경계 선택
6. 추가 레이턴시 및 프로토콜 영향 확인
7. 데이터와 제어 정렬
8. 최소 변경으로 RTL 수정
9. 합성/STA 재실행
10. 새 최악 경로 위치 확인
11. 집중 회귀 실행

## 10. rtl-verification-environment

**목적**: 재사용 가능한 RTL 시뮬레이션 및 검증 환경 구축/개선. 프로젝트 Phase 4~7 방법론 준수.

**핵심 규칙**:
- 재사용 가능한 인프라와 테스트케이스별 설정 분리
- 자극·프로토콜 구동·모니터링·체킹·골든 생성·리포팅 역할 구분
- 공유 AXI/메모리/프로토콜 BFM 및 외부 모델 재사용
- 설정 구동 테스트 선호 (TB 변형 복사 금지)
- SW와 RTL 간 자극/골든/레지스터 설정 단일 소스 공유
- 자동 pass/fail (웨이브폼 검사 없이 단위 검증 가능)
- 허용 오차를 명시적으로 정의
- 실패 시드 저장

**Phase별 검증 플로우**:

| Phase | 내용 | 게이트 |
|---|---|---|
| Phase 4 - SIM Environment | TB 및 외부 모델 환경 구축 | 스모크 케이스 통과 (compile→run→check) |
| Phase 5 - Unit Verification | RTL 출력 vs 골든 비교 | 허용 오차 내 일치 |
| Phase 6 - Coverage & Case Generation | 지시적/랜덤 케이스 + 코너 케이스 (overflow, clipping, divide-by-zero, boundaries, first/last, backpressure) | 기능 커버리지 목표 달성, 미해결 실패 = 0 |
| Phase 7 - System/Top Integration | 핸드셰이크·라인 버퍼 오버플로우·대역폭/레이턴시·CDC·멀티 IP 메모리 경합·성능 | E2E 골든 매치, 성능 목표, CDC 클린 |

**재사용 가능한 컴포넌트**:
- 클록/리셋 생성기
- AXI/프로토콜 BFM
- 메모리 모델
- 테스트케이스/설정 기술자
- 자극 생성기, 모니터, 체커/스코어보드
- 골든/레퍼런스 러너
- 타임아웃/에러/리포트 유틸리티
- 케이스 생성기, 회귀 런처/목록
- 어설션/커버리지 훅

> UVM이 아닌 경량 프레임워크를 사용하는 기존 프로젝트에서는 UVM 강제 금지.
